## Reproducción

Con IDB real (infra de F1.0.1):

1. Empleado `{id, name, active:false, deletedAt:<ts>}` guardado vía camino normal de persistencia.
2. El store crudo SÍ conservaba `deletedAt`.
3. Tras `loadApplicationData()`, el registro EN ESTADO tenía `deletedAt: undefined`.
4. Punto exacto de pérdida: **`PersistenceService.js:1097` — `new Employee(e)`** durante la inflación de carga.
5. Agravante: el aplanamiento del proxy (`toRaw`, hallazgo H-07) perpetúa la pérdida en cada guardado posterior ⇒ el empleado borrado "resucita" silenciosamente.

## Corrección aplicada (6 líneas, `js/modules/features/employees/Employee.js`)

Patrón condicional espejando el tratamiento existente del campo `photo`:

```js
// constructor:
if (hasOwnProperty(data,'deletedAt')) this.deletedAt = data.deletedAt;

// toJSON():
if (hasOwnProperty(this,'deletedAt')) json.deletedAt = this.deletedAt;
```

**Por qué condicional:** la AUSENCIA del campo debe distinguirse de `null` — así los payloads de empleados nunca borrados quedan byte-idénticos (cero ruido en sync/watermarks/diffs).

## Protección permanente

`js/tests/EmployeeTombstoneSurvival.test.js` (91 líneas): ciclo guardar→cargar→re-inflar contra IDB real afirma que `deletedAt` sobrevive end-to-end. Evidencia TDD: **RED pre-fix (2× undefined) → GREEN post-fix (2/2)**.

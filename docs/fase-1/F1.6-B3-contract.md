## 1. ON/OFF matrix (schema2 / schema3 native / promoted-legacy)

| Flag | Store read/write | Repository | Legacy handling | Gate |
|---|---|---|---|---|
| **OFF** | Global (`periodKey`, `closedAtId`, `statusClosedAtId`); no `projectId` filter; legacy schema2 preserved byte-identical | Global queries (`closedAt`/`status+closedAt`/`periodStart+periodEnd`), direct `loadById(id)` | No promotion; no migration | `assertTandaBBlockedWhenScoped` not triggered (`isProjectsEnabled()===false`) |
| **ON** | Project-scoped (`projectId`, `projectClosedAtId`, `projectStatusClosedAtId`); `captureScopedProjectId()`+`ensureNotStale()`; `ownsClosure()` filters | **Contract frozen still-global** until B3.3 — adding `where(projectId==pid)` now would hide schema2 rows (see §2) | No bulk migration; lazy promotion only (default project) | Tanda B blocked (`PayrollClosureStore.save`, `PayrollClosureRepository.*`, `PayrollClosureSync.*`) — until B3 opens slice-by-slice |

Schema variants:

- **schema2**: legacy, no `projectId`/`identityKind`/`ownershipToken`; `id = stableToken(fingerprint|after:predecessor)`.
- **schema3 native**: `projectId` canonical mandatory, `schemaVersion===3`, `id = stableToken(fingerprint|project:pid|after:predecessor)`, `fingerprint = JSON(snapshot{projectId,periodStart,periodEnd,rows})`.
- **schema3 promoted-legacy**: `schemaVersion===3`, `projectId=defaultCanonical`, `identityKind==='promoted-legacy'`, `ownershipToken=stableToken(id|fingerprint|project:pid)`, `id` unchanged (legacy id retained).

## 2. Legacy discovery strategy

Adding `where('projectId','==',pid)` on day 1 hides every schema2 row (no field). Therefore:

- **Do not** switch repository to scoped queries until discovery is fenced.
- **Default canonical only**: discovery/promotion applies solely to the default canonical `projectId` (the single project that inherits legacy data). Non-default projects A/B must not discover schema2; they start empty.
- **No bulk migration**: no cloud-side mass rewrite of schema2->schema3. Promotion is lazy, metadata-only, on read when the default project loads (B3.2 local stamper + future B3.3 cloud lazy path).
- **No mixing native results**: a scoped query must not return schema2 rows re-labeled as scoped; schema2 rows stay invisible to scoped queries until promoted, then appear as `promoted-legacy`.

## 3. Transition rules

| Transition | Allowed | Notes |
|---|---|---|
| schema2 -> promoted-legacy | YES (metadata-only) | `promoteLegacyPayrollClosure(closure, defaultPid)` only; preserves `id`/`fingerprint`/`rows`/`totals`; sets `projectId`+`identityKind`+`ownershipToken`; re-promotion idempotent, owner mismatch throws. |

| schema3 -> schema2 | FORBIDDEN | Downgrade never allowed; guards must reject. |

## 4. Rules model (wildcard bypass)

Current `firestore.rules:6` uses `match /users/{userId}/{document=**}` which matches **every** subcollection including `payrollClosures`. This is a bypass: any `users/{uid}/payrollClosures/{id}` inherits the broad read/write allow.

Contract (not yet applied): exclude `payrollClosures` from the wildcard or restructure matches so `payrollClosures` has its own rule with `projectId==request.resource.data.projectId` / ownership checks. `firestore.rules` stays unchanged in B3.0; tests assert the wildcard still covers `payrollClosures`.

## 5. loadById semantics and owner-check

Today `PayrollClosureRepository.loadById(id):138` does `getDoc(doc(db,'users',uid,'payrollClosures',id))` with no `projectId` check. `PayrollClosureSync.pullDetail(id):93` then `localStore.save(closure)` ingests that document directly.

Leak: caller in project A can `pullDetail(idFromB)` (id guessed/shared via summary) and persist B's detail locally as A — violates §1 invariant.

Frozen contract: `loadById` stays direct. B3.3 must add owner validation (check `doc.projectId===capturedPid` or reject) before `save`; tests assert the leak surface exists.

## 6. LiveSync dormant until B3.5

`closureSummary()` (`PayrollClosureRepository.js:66`) returns `{schemaVersion,id,fingerprint,periodStart,periodEnd,periodSource,status,closedAt,closedBy,updatedAt,totals,employeeCount,undoUntil,supersedesId,voidedAt,voidedBy,voidReason}` — **no `projectId`/`identityKind`/`ownershipToken`**.

`PayrollClosureRepository.subscribeRecent` + `PayrollClosureSync.subscribeRecent` + `PayrollClosureLiveSync.start` therefore cannot enforce ownership. Contract: LiveSync stays dormant (never auto-started; `app.js` has no `PayrollClosureLiveSync.start(`). B3.5 must add `projectId`+`identityKind`+`ownershipToken` to summary and gate `importClosures` before activating.

## 7. Queries and indexes

Existing: `firestore.indexes.json` has single composite `status ASC, closedAt DESC, __name__ DESC` on `payrollClosures`.

Required (justified):

- `projectId ASC, closedAt DESC, __name__ DESC` — pagination `listPage`/`loadPage` per project.
- `projectId ASC, status ASC, closedAt DESC, __name__ DESC` — filtered pagination.

Provisional (not added until proven):

- `projectId ASC, periodStart ASC, periodEnd ASC` (or with `closedAt`) — `loadByPeriod` currently uses two `where` without ordering; stays without composite until a real `FAILED_PRECONDITION` test reproduces the need. Do not add speculatively.

## 8. Capture-before-await / stale completion

`PayrollClosureStore` contract (`PayrollClosureStore.js:42,51`):

- `captureScopedProjectId()` captures `pid` from `captureEntityProjectScope()` **before** any `await` (`db.get`/`query`/`getPageByIndex`).
- `ensureNotStale(pid)` re-checks `peekEntityScope()` **after** each await; if `!enabled` or `curPid!==pid` throws `PAYROLL_CLOSURE_STALE_READ`.
- `getById`/`getByPeriod`/`listPage`/`getSyncStates` all follow capture -> await -> ensureNotStale -> ownsClosure.

No floating promise may complete into a stale project. Same pattern will be required for repository when it becomes scoped.

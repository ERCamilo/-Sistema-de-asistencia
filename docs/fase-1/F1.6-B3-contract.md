## 1. ON/OFF matrix (schema2 / schema3 native / promoted-legacy)

| Flag | Store read/write | Repository | Legacy handling | Gate |
|---|---|---|---|---|
| **OFF** | Global (`periodKey`, `closedAtId`, `statusClosedAtId`); no `projectId` filter; legacy schema2 preserved byte-identical | Global queries (`closedAt`/`status+closedAt`/`periodStart+periodEnd`), direct `loadById(id)` | No promotion; no migration | `assertTandaBBlockedWhenScoped` not triggered (`isProjectsEnabled()===false`) |
| **ON** | Project-scoped (`projectId`, `projectClosedAtId`, `projectStatusClosedAtId`); `captureScopedProjectId()`+`ensureNotStale()`; `ownsClosure()` filters | Scoped query path implemented in B3.3 with default-only legacy fallback; public Tanda B gates remain blocked | No bulk migration; lazy promotion only (default project) | Tanda B blocked (`PayrollClosureStore.save`, `PayrollClosureRepository.*`, `PayrollClosureSync.*`) — until B3 opens slice-by-slice |

Schema variants:

- **schema2**: legacy, no `projectId`/`identityKind`/`ownershipToken`; `id = stableToken(fingerprint|after:predecessor)`.
- **schema3 native**: `projectId` canonical mandatory, `schemaVersion===3`, `id = stableToken(fingerprint|project:pid|after:predecessor)`, `fingerprint = JSON(snapshot{projectId,periodStart,periodEnd,rows})`.
- **schema3 promoted-legacy**: `schemaVersion===3`, `projectId=defaultCanonical`, `identityKind==='promoted-legacy'`, `ownershipToken=stableToken(id|fingerprint|project:pid)`, `id` unchanged (legacy id retained).

## 2. Legacy discovery strategy

Adding `where('projectId','==',pid)` on day 1 hides every schema2 row (no field). Therefore:

- **Do not** switch repository to scoped queries until discovery is fenced.
- **Default canonical only**: discovery/promotion applies solely to the default canonical `projectId` (the single project that inherits legacy data). Non-default projects A/B must not discover schema2; they start empty.
- **No bulk migration**: no cloud-side mass rewrite of schema2->schema3. Promotion is lazy, metadata-only, on read when the default project loads (B3.2 local stamper + B3.3 cloud lazy path).
- **No mixing native results**: a scoped query must not return schema2 rows re-labeled as scoped; schema2 rows stay invisible to scoped queries until promoted, then appear as `promoted-legacy`.

## 3. Transition rules

| Transition | Allowed | Notes |
|---|---|---|
| schema2 -> promoted-legacy | YES (metadata-only) | `promoteLegacyPayrollClosure(closure, defaultPid)` only; preserves `id`/`fingerprint`/`rows`/`totals`; sets `projectId`+`identityKind`+`ownershipToken`; re-promotion idempotent, owner mismatch throws. |
| schema2 -> schema3 native | NO | Native requires recomputed fingerprint+id; forbidden. |
| schema3 -> schema2 | FORBIDDEN | Downgrade never allowed; guards must reject. |
| schema3 owner change | FORBIDDEN | `promoteLegacyPayrollClosure` on already-promoted with different `projectId` throws; `voidPayrollClosure` asserts `assertPromotedLegacyClosure` invariant. |

## 4. Rules model (wildcard bypass) — B3.4 Unit 1 applied

Before B3.4 Unit 1, `firestore.rules:6` used `match /users/{userId}/{document=**}`. Firestore Rules matches are additive, so that pattern granted the broad account-owner allow to **every** subcollection, including `payrollClosures`, regardless of any narrower rule.

Unit 1 removes the overlapping user wildcard and gives `payrollClosures` its own match. The current application paths are explicitly owner-scoped: `data`, `employees`, `positions`, `leaders`, `attendance`, `snapshots`, `projects`, `cashPeriods`, `pettyCash`, `projectRegistryV1`, `projectsV1`, and `projectAliasesV1`. Unknown or nested user paths remain denied by the default rule. `mainSyncOutbox` is IndexedDB-only and `receipts` is Cloud Storage, so neither is a Firestore match.

The payroll match is owner-scoped for reads/deletes and validates server-visible document shape for creates/updates. Rules do not inspect `isProjectsEnabled()`, `localStorage`, or the client project registry. Schema2 remains an owner-compatible legacy shape; schema3 requires a non-empty `projectId` that is not the `legacy-unresolved:*` sentinel. Promoted legacy documents require the `promoted-legacy` marker and a non-empty `ownershipToken`, but Rules do not claim to recompute the opaque `stableToken` value.

`isCanonicalProjectId()` intentionally checks only the server-expressible non-empty string and forbidden-sentinel boundary. It does not trim or normalize client input. Exact whitespace normalization remains a client/model concern for B3.4 Unit 3 and is not fabricated as a Rules capability here.

Runtime Rules coverage remains unavailable: this repository has no Firestore emulator configuration or `rules-unit-testing` dependency. Unit 1 therefore uses static Rules-contract assertions and does not claim runtime allow/deny results.

### 4.1 Firestore Rules truth table — B3.1 freeze, Unit 1 enforcement

| # | Operation | Condition | Expected | Rationale / validation |
|---|-----------|-----------|----------|------------------------|
| 1 | create — schema2 legacy | `schemaVersion==2`, no `projectId`, owner `request.auth.uid==userId`, non-empty server-visible `id`/`fingerprint` | **ALLOW** | Preserve OFF contract; Rules cannot recompute the opaque legacy `stableToken` derivation |
| 2 | create — schema3 | `schemaVersion==3`, `projectId` present and canonical-shaped (non-empty, not `legacy-unresolved:*`) | **ALLOW only if canonical-shaped** | Reject if missing/invalid `projectId`; use a server-visible shape check, not self-comparison |
| 3 | update — schema2 → promoted-legacy | existing `schemaVersion==2` → `request.resource.data` has `schemaVersion==3`, `identityKind=='promoted-legacy'`, preserves identity/payload fields and sets canonical-shaped `projectId` + non-empty `ownershipToken` | **ALLOW (only this promotion path)** | Rules preserve fields and marker shape; they do not recompute the opaque token |
| 4 | update — schema3 → schema2 | `resource.data.schemaVersion==3` → `request.resource.data.schemaVersion==2` | **REJECT** | Downgrade never allowed |
| 5 | update — schema3 owner change | `resource.data.projectId` exists and `request.resource.data.projectId != resource.data.projectId` | **REJECT** | Owner immutable; correct check is `request.resource.data.projectId == resource.data.projectId`, NOT tautology `projectId == request.resource.data.projectId` |
| 6 | update — closed → voided | `resource.data.status=='closed'` → `request.resource.data.status=='voided'` with `voidedAt`/`voidedBy`/`voidReason` | **ALLOW** | Legitimate annulment |
| 7 | update — voided → closed | `resource.data.status=='voided'` → `request.resource.data.status=='closed'` | **REJECT** | Irreversible void |
| 8 | wildcard bypass | `match /users/{userId}/{document=**}` granting `payrollClosures` as alternative allow | **MUST NOT** | Generic wildcard must exclude `payrollClosures` or be restructured so `payrollClosures` has its own scoped match; otherwise any `projectId` bypass succeeds |

Notes: the tautology `projectId == request.resource.data.projectId` is invalid (always true on create). Unit 1 uses `isCanonicalProjectId(request.resource.data.projectId)` for the server-visible create shape and `request.resource.data.projectId == resource.data.projectId` for update immutability. Neither the client feature flag nor `stableToken` is evaluated by Rules.

## 5. loadById semantics and owner-check

## 7. Queries and indexes

Current after B3.4 Unit 2: `firestore.indexes.json` has five `payrollClosures` collection indexes: the preserved legacy `status ASC, closedAt DESC, __name__ DESC` index plus the four scoped composites below.

Required (justified):

- `projectId ASC, closedAt DESC, __name__ DESC` — pagination `listPage`/`loadPage` per project.
- `projectId ASC, status ASC, closedAt DESC, __name__ DESC` — filtered pagination.
- `schemaVersion ASC, closedAt DESC, __name__ DESC` — schema-aware pagination across legacy and promoted/native records.
- `schemaVersion ASC, status ASC, closedAt DESC, __name__ DESC` — schema-aware filtered pagination.

Provisional (not added until proven — B3.2 outcome: not needed for equality-only, kept out of `firestore.indexes.json`):

- `projectId ASC, periodStart ASC, periodEnd ASC` (or with `closedAt`) — `loadByPeriod` currently uses two `where` without ordering; stays without composite until a real `FAILED_PRECONDITION` test reproduces the need. Do not add speculatively.
- **B3.2 preflight finding**: `where(projectId==pid)+where(periodStart==X)+where(periodEnd==Y)` is **three equality filters, no range, no `orderBy`** → Firestore merges single-field indexes (see [index overview — use index merging](https://firebase.google.com/docs/firestore/query-data/index-overview) + docs `where(projectId==)+where(periodStart==)+where(periodEnd==)` = no composite). Composite is only required when adding range/inequality or `orderBy` on a different field. See §11.

## 11. B3.2 preflight — equality-only index + emulator + Rules verifiability (no productive change)

> B3.2 is doc+tests only. No `PayrollClosureRepository`, `firestore.rules`, or `firestore.indexes.json` mutation. Findings frozen here so B3.4 does not lose nuance.

### 11.1 Index need: does `projectId==pid + periodStart==X + periodEnd==Y` require composite?

**Resolved: NO — not with current shape.**

- Current `loadByPeriod` is `where('periodStart','==',…)+where('periodEnd','==',…)`, no `orderBy`. Future scoped form would be `where('projectId','==',pid)` + same two equalities, still **three equality filters, no range, no `orderBy`** (see `PayrollClosureRepository.js:145`).
- Firestore merges single-field indexes for equality-only queries: "[Can] re-use existing indexes … merge the indexes for simple equality filters to build the composite indexes needed for larger equality queries" — [index overview](https://firebase.google.com/docs/firestore/query-data/index-overview). Equality → no dedicated composite; composite required only with range/inequality or `orderBy` on different field.
- Therefore `projectId ASC, periodStart ASC, periodEnd ASC` (or with `closedAt`) is **provisional and NOT added** to `firestore.indexes.json` in B3.2. Adding it "just in case" would violate work-unit rule and incur spurious storage/maintenance.
- If B3.3/B3.4 later adds `orderBy('closedAt')` or a range filter to `loadByPeriod`, the need must be reproven with a real `FAILED_PRECONDITION` reproduction against production (or emulator with enforcement) before adding any index.

### 11.2 Emulator / `FAILED_PRECONDITION` reproduction attempt

Attempted deterministic repro: query `where('projectId','==',pid)+where('periodStart','==',X)+where('periodEnd','==',Y)` and expect `code === 'failed-precondition'` with index-creation URL on missing index (production behavior).

**Finding: not reliably reproducible in this repo’s environment.**

- Official emulator contract: "The emulator does not track composite indexes and will instead execute any valid query. Make sure to test your app against a real Firestore instance to determine which indexes you require." — [Use Firestore emulator locally — Indexes](https://cloud.google.com/firestore/native/docs/emulator#indexes) and [Test Datastore Mode — Indexes](https://docs.cloud.google.com/datastore/docs/emulator#indexes). Same note in bug reports and community docs: emulator by default never throws `FAILED_PRECONDITION` for missing composite index.
- Some setups expose `FIRESTORE_EMULATOR_ENABLE_INDEX_ENFORCEMENT` / REST index creation, but this repo has no emulator harness, no `firebase.json` emulator config requiring indexes, and `js/tests` mock Firestore via `jest` mappers — so no deterministic `FAILED_PRECONDITION` surface exists.
- Decision: the equality-only period index remains **provisional and absent from `firestore.indexes.json`** (see §7). The `PayrollClosureB3Preflight` test documents this emulator limitation explicitly and asserts the five query-shape indexes without fabricating a fake failure.

### 11.3 Rules verifiability nuance applied in B3.4 Units 1/2 (Unit 3 pending)

Rules cannot know client-only feature flag — B3.4 Units 1-3 must not claim Rules branches on `isProjectsEnabled()`.

B3.1 truth table (§4.1) remains the semantic contract. Units 1/2 preserve its Firestore-expressible boundary; Unit 3 must preserve this limitation:

| Concern | Nuance to preserve | Implication for B3.4 |
|---------|-------------------|----------------------|
| Client-only feature flag (`isProjectsEnabled()` / schema2 OFF) | Rules cannot read client memory/offline flag or `localStorage`. Row "create schema2 OFF" has no server-visible signal; Rules sees only the document shape. | **Do not claim Rules knows ON/OFF.** In B3.4 either (a) define a server-visible signal (e.g., `schemaVersion==2` as legacy owner path, distinct from `schemaVersion==3` scoped path) or (b) accept schema2 as legacy owner path (ALLOW if `request.auth.uid==userId` + valid legacy identity), without branching on client flag. Doc must state this explicitly. |
| `defaultCanonical` / `promoted-legacy` ownership | `defaultCanonical` is client-derived (canonical project list); Rules has no access to project registry. `ownershipToken == stableToken(id|fingerprint|project:pid)` is opaque client hash. | Only enforce what Firestore can verify: `projectId` is non-empty canonical-shape (e.g., `isValidProjectId` = non-empty string, not `legacy-unresolved:*`), `identityKind == 'promoted-legacy'` presence, and immutability `request.resource.data.projectId == resource.data.projectId`. Do **not** attempt to recompute `stableToken` server-side unless a verifiable derivation is exposed; if not verifiable, document as client contract with server-side immutability guard. |
| `defaultCanonical` / `ownershipToken` validation | Over-validating unverifiable tokens would reject legitimate legacy promotions; under-validating would accept spoofed claims. | B3.4 must phrase validations as "only if Firestore-expressible and verifiable" — enforce non-empty `projectId`, canonical shape, and preservation of `id`/`fingerprint` on promotion; treat `ownershipToken` as integrity hint, not as recomputable proof, unless Firestore function can reproduce it. |

Preserved literal keys for search: `defaultCanonical/ownershipToken` — only enforce if Firestore-expressible and verifiable.

If B3.4 over-claims Rules awareness of client flag or recomputability of `ownershipToken`, the contract silently diverges from enforceable reality. This appendix is the source of truth for that constraint.

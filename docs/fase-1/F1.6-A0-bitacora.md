## Resumen evaluable

Se corrigió la deduplicación global de `IndexedDBService.saveState` que colisionaba `#12 de A` contra `#12 de B` al persistir empleados y líderes. Con flag ON cada clave de dedup incluye proyecto efectivo (`project:<id>:num:42`); con flag OFF se conserva paridad byte-exacta `num:`/`id:` legacy; los registros legacy sin `projectId` ni default autoritativo quedan en namespace interno `legacy-unresolved:*` que nunca se persiste ni colisiona con namespaces explícitos. La unidad queda aislada en un módulo nuevo (`EntityProjectScope.js`) y 4 archivos integrados, con 2 suites enfocadas nuevas/bloqueadas (12/12 + 13/13) y validación acotada **7 suites · 76 tests**. Cualquier agente futuro puede evaluar A0 leyendo solo esta bitácora + el diff de `c7a9e0c`.

## 2. Descubrimientos / Decisiones

### 2.1 Tríada de fallos — 3 ciclos RED→GREEN que sostienen el contrato

| Ciclo | RED observado | GREEN y causa raíz |
|---|---|---|
| **1 — Clave sin scope** | `RecordKey` esperaba `project:PRJ-A:num:42` y `project:PRJ-D:num:42` pero retornó `num:42`. IDB real: `employees:1`, `leaders:1`, `deduplicated:2` — registros de A desaparecieron (dedup global). | Extracción de `EntityProjectScope`; `dedupKeyForRecord` con scope; OFF paridad exacta; legacy→default. Suites iniciales: RecordKey **12/12**, F1.4 **9/9**, contexto **33/33**, IDB/tombstones **6/6**. |
| **2 — Scope stale en transición same-graph** | Revisión fresh-context detectó cache reutilizado al cambiar flag sin `getEntityScope()` intermedio. **OFF→ON:** `employees:2`, `leaders:1`, `deduplicated:4` — se perdían registros (scope deshabilitado cacheado). **ON→OFF:** `employees:2`, `leaders:2`, `deduplicated:0` — no se restauraba dedup global legacy. | Capturar `flag + default` **una vez por `saveState`** y propagar ese snapshot a todas las claves. GREEN: F1.4 **11/11**, RecordKey **12/12**, proyectos/default/context/boot **49/49**, IDB/tombstones **6/6**. Estadísticas: OFF→ON `employees:4`/`leaders:2`/`deduplicated:1` (solo colisión legacy `#13`); ON→OFF `employees:1`/`leaders:1`/`deduplicated:2` (paridad legacy restaurada). |
| **3 — Fallback obsoleto de default** | `captureEntityProjectScope()` usaba `readDefaultProjectId() ?? resolvedScope.defaultProjectId`. Si el puntero autoritativo actual está ausente, el fallback reutilizaba un `PRJ-OLD` cacheado obsoleto. Un legacy sin resolver se clasificaba bajo `PRJ-OLD` y se deduplicaba destructivamente contra un registro explícito `PRJ-OLD:num:12` (pérdida silenciosa). | Corrección final `c7a9e0c`: ausencia del puntero actual **no** promueve valor cacheado. Un legacy sin default autoritativo queda `legacy-unresolved`. Caso final GREEN **1/1** (`F14IsolationBattery S2e`); persistencia **13/13**. |

### 2.2 Contrato final de A0

- `record.projectId` explícito tiene prioridad.
- Si no existe, se usa el default autoritativo actual (`localStorage.getItem(DEFAULT_PROJECT_LS_KEY)` leído dentro de `captureEntityProjectScope()`).
- Si tampoco existe, el registro queda **legacy no resuelto**.
- Un legacy no resuelto usa clave interna `legacy-unresolved:<recordKey>` (p. ej. `legacy-unresolved:num:12`); **nunca** persiste un sentinel `projectId` ni se deduplica con un namespace explícito `project:*` — garantiza que `#12` legacy y `#12` explícito de `PRJ-OLD` coexistan (ver `F14IsolationBattery.test.js:305` — ambos sobreviven con `deduplicated:0`).
- Con flag OFF se conserva **paridad exacta** `num:`/`id:` legacy aunque los registros porten `projectId` (ver `IndexedDBSaveStateKeyTests.js:55`).
- `effectiveProjectId`/`sameEffectiveProject` mantienen hasOwnProperty: ausencia de `projectId` es ausencia, no `null` persistido.

## Resumen evaluable

Se implementó el gate mínimo SA-only que faltaba antes de cualquier estado económico durable por `projectId` o cloud: la misma cuenta/obra resuelve el mismo `projectId` canónico en todos sus dispositivos, con `activeProjectId` como selección local. El registro `users/{uid}/projectRegistryV1/default` promociona atómicamente el primer proyecto local como canónico (fast-path `getDoc` + `runTransaction`), los alias `users/{uid}/projectAliasesV1/{legacyId}` resuelven retrocompatibilidad directa sin cadenas, y la adopción local reescribe de forma idempotente y reanudable todos los portadores de scope (IDB `projects`/`employees`/`positions`/`leaders`/`attendance`+tombstones, punteros LS y `EntityProjectScope`, `mainSyncOutbox`). Flag OFF mantiene paridad exacta, offline funciona provisional y recupera tras la primera canonicalización cacheada, y el aislamiento por `uid` (G1–G5) evita fuga entre cuentas. Cualquier agente futuro puede evaluar A0.5 leyendo solo esta bitácora + el diff de `51a7611` + `ProjectIdentityA05.test.js:1`.

### 2.2 Algoritmo de promoción y carrera (race)

```
ensureCanonicalProject({uid, localProject}):
  if !isProjectsEnabled() → {canonicalId: localId, status:'flag-off'}
  if !uid o !isValidProjectId(localId) → provisional/flag-off

  // Fast path optimista (sin contención)
  ex = await getCanonicalId(uid)               // getDoc(users/{uid}/projectRegistryV1/default)
  if ex → cacheCanonical(ex) → return {ex, status:'existing'|'already-canonical'}

  // Contención — transacción atómica
  canonical = await runTransaction(db, async tx => {
    snap = await tx.get(registryRef)           // tx.get, no getDoc fuera
    if snap.exists() && isValidProjectId(snap.canonicalProjectId) → return snap.canonicalProjectId
    now = serverTimestamp(); dev = getDeviceId()
    tx.set(registryRef, {canonicalProjectId:localId, createdAt:now, updatedAt:now, createdBy:uid, createdByDeviceId:dev})
    tx.set(projectRef(localId), {id:localId, name:..., status:..., schemaVersion:..., createdAt, updatedAt})
    return localId
  })
  cacheCanonical(canonical)
  return {canonical, status: canonical===localId ? 'promoted' : 'race-existing'}
  catch → getCanonicalId(uid) retry → {canonicalId: again, status:'race-existing-retry'} o provisional
```

Propiedades: exactamente un canónico por `uid` aunque dos dispositivos promuevan simultáneamente; `tx.get` dentro de la transacción es la única lectura autoritativa bajo contención; cache `asistencia_canonical_{uid}` permite operar offline tras la primera canonicalización exitosa.

### 2.4 Resolución de alias — directos sin cadenas

- Cada `legacyId` mapea directo a su `canonicalId` canónico; no existe alias `A→B` donde `B→CANON`. Tres dispositivos con `PRJ-A`/`PRJ-B`/`PRJ-C` adoptan cada uno directo a `PRJ-CANON` (p. ej. `PRJ-B→PRJ-A` donde `PRJ-A` es canónico, y `PRJ-C→PRJ-A` directo, no `PRJ-C→PRJ-B→PRJ-A`).
- Ingress: `resolveCanonicalAlias(uid, legacyId)` lee `projectAliasesV1/{legacyId}` y cachea; si Firestore falla o no existe, retorna cache o `legacyId` intacto (offline).
- Egress: toda escritura futura usa `projectId` ya reescrito (outbox mirror/daily/entities) — el payload que sube a la nube es canónico, no alias.
- Test 10 fija que dos alias a `PRJ-C` directos no se encadenan; test 16 fija el escenario 3-device con exactly-one-canonical (`ProjectIdentityA05.test.js:384`).

### 2.7 Paridad flag OFF y offline

- **Flag OFF:** `ensureCanonicalProject` retorna `{canonicalId: localId, status:'flag-off'}` sin tocar Firestore (`getDoc`/`runTransaction`/`setDoc` no se llaman); `resolveCanonicalAlias` retorna `legacyId` identidad; `adoptProject` retorna `{skipped:true, reason:'flag-off'}`. Test 1 lo fija (`ProjectIdentityA05.test.js:68`). Flag OFF después de canonicalización deja LS pointers intactos para cuando se reactive, pero scope se resetea y adopción queda deshabilitada (test 12).
- **Offline provisional:** `getDoc`/`runTransaction` que lanzan (p. ej. `offline`) retornan `{canonicalId: localId, status:'provisional-*'}` sin cachear; test 2. Tras la primera promoción exitosa, `asistencia_canonical_{uid}` queda cacheado y `getCanonicalId` lo retorna aunque `getDoc` falle, permitiendo operar offline con normalidad (test 3). Sinergia: un dispositivo que nunca canonicalizó trabaja provisional; en cuanto canonicaliza una vez, todos sus futuros arranques offline usan el cache hasta reconectar.

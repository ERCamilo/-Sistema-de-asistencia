## Propuestas técnicas (esperando OK de Dirección)

### P3 — Asistencia multiproyecto (F1.0.3)

**Contexto:** el documento cloud `users/{uid}/attendance/{dateKey}` guarda TODOS los registros de ese día en un mapa `records`. Con dos proyectos activos, ambos escriben el MISMO documento diario.

**Decisión propuesta (ADR-008):**
1. La ruta diaria NO cambia (minimiza invasión).
2. Cada registro dentro de `records` gana su propio `projectId`.
3. Toda escritura del día sigue siendo read-merge-write, pero el merge filtra: leer doc completo → modificar SOLO registros del proyecto activo → conservar intactos los demás → guardar.
4. **Invariantes obligatorios (tests antes de dar F1.5 por terminada):**
   - Guardar asistencia de A no altera ningún registro de B del mismo día (y viceversa).
   - Un registro sin `projectId` = proyecto predeterminado (regla fundacional F0.4 §2).
   - El podador de retención local (60 días) nunca borra el día completo si otro proyecto aún tiene registros vivos en él.
5. Clave local IDB `${employeeId}-${date}` queda libre de colisiones porque los ids de empleado son únicos globales (ver P6).

### P4 — Espejo `data/current` (F1.0.4)

**Decisión propuesta (ADR-009 — opción A elegida por Dirección):**
1. El espejo permanece a nivel cuenta y contiene TODOS los proyectos conocidos localmente.
2. Cambiar `activeProjectId` es SOLO un cambio de contexto de UI/repositorios; jamás dispara un `saveFullState()` que excluya entidades del proyecto saliente.
3. **Invariante obligatorio (test antes de habilitar dos proyectos activos):** estando en B tras usar A, guardar estado → el espejo resultante conserva empleados/asistencia/nómina de A byte-a-byte equivalentes.
4. `saveFullState` gana campo informativo con el registro de proyectos (lista/versiones) cuando F1 lo defina; limpieza de `exportConfig` del espejo según H-05 (no bloqueante).

### P5 — Fechas reales del proyecto (F1.0.5)

**Decisión propuesta (ADR-011):** añadir a Project v1:
- `startDate?: number|null` — inicio laboral/contractual real (puede ser anterior al alta en SA).
- `endDate?: number|null` — fin real de obra.
- `closedAt` sigue siendo el cierre ADMINISTRATIVO (cuándo alguien pulsó Cerrar).
- Regla de informe: informe usa `endDate ?? closedAt` como finalización y `startDate ?? createdAt` como inicio.
- Ambas editables desde UI de proyecto (F2); null permitido siempre.

### P6 — Significado exacto de "copiar empleado" (F1.0.6)

**Decisión propuesta (ADR-010):**
- Copiar ⇒ crear ficha NUEVA con nuevo `employeeId` + `copiedFromEmployeeId` (auditoría; cero sincronización posterior).
- **Se copia:** `number` (el número es por-proyecto en Gen1), `name`, `positions[]` (remapeadas a los puestos clonados del nuevo proyecto), salarios/configuración horaria, `phone/email`, notas libres.
- **NO se copia (historial/movimientos):** `loans[]`, `advances[]`, `bonuses[]`, `deductions[]`, `statusHistory[]`, fechas de auditoría (nuevas).
- Orden obligatorio de clonación de proyecto: líderes → puestos → empleados (los empleados necesitan los ids nuevos de puestos). Queda registrado como dependencia interna de F2.7.
- Mensaje para Integración/Mini (cuando corresponda, F3): en Gen1, `employeeId` = ficha-por-proyecto; NO es identidad global de persona.

### P7 — Mapping Project oficial ↔ PettyCashProject (F1.0.7 / DEP-SA-001)

**Diseño decidido (implementación diferida, decisión congelada ya):**
1. `pettyCashProjects` gana campo nullable `officialProjectId`.
2. Backfill único e idempotente: TODO pettyCashProject existente apunta al Proyecto Predeterminado.
3. Todo pettyCashProject nuevo nace ligado al proyecto activo oficial.
4. Los reportes F2.8/F2.9 leen caja vía ese vínculo; si está ausente → dato huérfano visible en diagnóstico (nunca silencioso).
5. No se reescriben colecciones ni lanes de sync de caja en esta etapa.

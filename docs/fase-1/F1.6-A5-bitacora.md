## Resumen evaluable

A5 trata `exportConfig` como estado transitorio de UI/sesión (selección de período, inclusión de preview, selección de préstamos, scopes de ajustes, etc.) y lo sanea simétricamente en **todas las fronteras de egreso e ingreso**: nunca se persiste a mirror, replace cloud, snapshots ni payload `local→cloud` de DataOps, y nunca resucita en ingresos legacy (mirror subscription, snapshot/cloud restore, backup import, `prepareRestoredState`). El helper centralizado `sanitizeExportConfig(stateClone)` elimina **únicamente** la propiedad `exportConfig` y preserva configuración durable legítima (`settings.payrollDefaults`, `projectPayrollConfigs`). Verifica que un `exportConfig` viejo no resucite tras sync/restore/snapshot load, con garantías **A→B→A preservadas desde A4** y paridad **OFF** intacta. No toca `PayrollClosure`, cierres, préstamos, ajustes económicos, PDF, SplitX, economic cloud ni petty cash. No amplía persistencia de `exportConfig` y no implementa B ni F1.7.

## 2. Contratos exactos

### 2.1 Helper centralizado

- `sanitizeExportConfig(stateClone)` en `js/modules/services/ExportConfigSanitizer.js:20` — guarda `if (!stateClone || typeof stateClone !== 'object') return stateClone`; luego `if ('exportConfig' in stateClone) delete stateClone.exportConfig`; retorna `stateClone`.
- Elimina **solo** la propiedad de primer nivel `exportConfig`; no recorre ni borra claves anidadas ni otras propiedades.
- Es el único import H-05 en cada frontera (`FirebaseService.js:8`, `PersistenceService.js:14`, `DataOps.js:11`, `app.js:12`); no existe sanitización ad-hoc duplicada.
- Idempotente: llamar dos veces no altera el resultado; segunda llamada es no-op si ya no existe `exportConfig`.

### 2.2 Egreso — `exportConfig` nunca persiste ni se publica

- `FirebaseService.saveFullState` (`FirebaseService.js:498`) — sanea `snapshotContext` vía `sanitizeExportConfig(snapshotContext)` antes de `JSON.parse(JSON.stringify(snapshotContext))` para `cleanState` del mirror.
- `FirebaseService.replaceCloudFull` (`FirebaseService.js:534`) — sanea `snapshotContext` antes de clonar para el documento `data/current` de reemplazo.
- `FirebaseService.createSnapshot` (`FirebaseService.js:574`) — sanea `snapshotContext` antes de clonar para snapshot, tras `sanitizePettyCashForSnapshot`.
- `PersistenceService` (`PersistenceService.js:312`) — camino feliz sanea `_mirrorSnapshot` tras `getState()`; catch hace `Object.assign(_mirrorSnapshot, stateManager.getState())` luego `sanitizeExportConfig(_mirrorSnapshot)` + `delete _mirrorSnapshot.exportConfig` idempotente antes de `syncFirebaseMirrorDebounced`.
- `DataOps` (`DataOps.js:412`) — rama `replaceLocalWithCloud` local→cloud sanea `frozen` (`sanitizeExportConfig(frozen)`) antes de upload del payload congelado.

### 2.3 Ingreso — `exportConfig` legacy nunca resucita

- `FirebaseService.getSnapshot` (`FirebaseService.js:602`) — si `state && typeof state === 'object'` sanea `state` antes de retornar el snapshot al caller.
- `FirebaseService.getFullState` (`FirebaseService.js:630`) — si `data && typeof data === 'object'` sanea `data` antes de retornar el estado cloud.
- `DataOps.replaceLocalWithCloud` (`DataOps.js:378`) — sanea `cleanCloud` antes de `Object.assign(state, cleanCloud)`; el test verifica `indexOf(sanitize) < indexOf(assign)`.
- `app.js:applyRemoteData` (`app.js:842`) — sanea `remoteData` antes de aplicar el mirror entrante al estado.
- `app.js:applyBackupData` (`app.js:1218`) — sanea `data`, `importedData` y `data.state` si existen antes de sobrescribir el estado (atomicidad local).
- `app.js:restoreSnapshot` / `prepareRestoredState` (`app.js:1184`) — sanea `snapshot.state` antes de `prepareRestoredState(snapshot.state)`.

### 2.4 No se elimina configuración durable legítima

- El helper borra exclusivamente `exportConfig`; nunca toca `settings`, `settings.payrollDefaults`, `settings.companyName`, `projectPayrollConfigs` ni `payrollConfigsV1`.
- Tests verifican: tras `sanitizeExportConfig`, `settings.payrollDefaults.regularHoursPerDay` permanece (`8` o `6` según caso), `projectPayrollConfigs[0].projectId` permanece (`PRJ-A`), y `JSON.stringify(state.settings)` es idéntico antes/después salvo por la ausencia de `exportConfig`.
- Fuera de alcance explícito: no se modifica `PayrollClosure`, cierres, préstamos, ajustes económicos, PDF, SplitX, economic cloud ni petty cash.

### 2.5 Preservación de garantías A4 y OFF

- Con flag ON, A→B→A sigue reconstruyendo el durable de A en sesión fresca sin arrastrar estado stale; múltiples sanitizaciones no eliminan `settings.payrollDefaults`/`projectPayrollConfigs` de A ni B (test A→B→A preserva `regularHoursPerDay` 6→8→6).
- Con flag OFF, la ruta legacy permanece byte-idéntica; `sanitizeExportConfig` es no-op si no hay `exportConfig` o si el objeto no lo contiene; no altera `settings.payPeriod` ni campos visuales.
- No se habilitan cierres, préstamos, ajustes persistidos/programados, historial ni exportación final; `ScopedPayrollTab` sigue siendo solo preview base.

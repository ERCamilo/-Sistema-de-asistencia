## 1. Exact wire contract (literals)

### 1.1 Envelope `attendance-submission/v1` — Mini → SA (bare JSON body)

Minimal valid body (required keys only):

```json
{
  "schema": "attendance-submission/v1",
  "submissionId": "123e4567-e89b-42d3-a456-426614174000",
  "saProjectId": "PRJ-EJEMPLO-0001",
  "scope": { "ownerUid": "owner-1", "siteId": "obra-1", "sourceId": "mini-principal" },
  "deviceId": "phone-1",
  "rosterVersion": "roster-3",
  "capturedAt": "2026-09-07T12:00:00.000Z",
  "workDate": "2026-09-06",
  "rows": [
    {
      "miniLocalId": "mini-u1",
      "number": "001",
      "name": "Ana",
      "normalHours": 8,
      "overtimeHours": 0,
      "status": "present"
    }
  ]
}
```

Full body with all optionals:

```json
{
  "schema": "attendance-submission/v1",
  "submissionId": "223e4567-e89b-42d3-a456-426614174001",
  "saProjectId": "PRJ-EJEMPLO-0001",
  "scope": { "ownerUid": "owner-1", "siteId": "obra-1", "sourceId": "mini-principal" },
  "deviceId": "phone-1",
  "rosterVersion": "roster-3",
  "capturedAt": "2026-09-07T12:00:00.000Z",
  "workDate": "2026-09-06",
  "rows": [
    {
      "miniLocalId": "mini-u1",
      "number": "001",
      "name": "Ana",
      "normalHours": 7.5,
      "overtimeHours": 0.5,
      "status": "present",
      "saEmployeeId": "EMP-001"
    }
  ],
  "clientSequence": 7,
  "excludedCount": 2,
  "errorSummary": { "unparsedFragments": 2, "codes": ["UNPARSED_LINE"] }
}
```

| Key | Required | Type / rule |
|---|---|---|
| `schema` | ✔ | literal `attendance-submission/v1` |
| `submissionId` | ✔ | UUID (message id, not employee/project identity) |
| `saProjectId` | ✔ | canonical normalized SA ID: trimmed, 1–128 chars, no whitespace/control (§3) |
| `scope` | ✔ | exact `{ownerUid, siteId, sourceId}`, each trimmed non-blank; audit-only, never project authority (§1.3) |
| `deviceId` | ✔ | trimmed non-blank string (opaque) |
| `rosterVersion` | ✔ | trimmed non-blank string, opaque; equality only (§6) |
| `capturedAt` | ✔ | strict ISO-8601: `new Date(v).toISOString() === v` |
| `workDate` | ✔ | strict calendar `YYYY-MM-DD` (regex + real month/day + UTC round-trip) |
| `rows` | ✔ | non-empty array of §1.2 rows |
| `clientSequence` | — | positive safe integer (`>= 1`); ordering hint only |
| `excludedCount` | — | safe integer `>= 0`; partial-capture count (§5) |
| `errorSummary` | — | exact `{unparsedFragments: int >= 0, codes: string[]}`; audit hint (§5) |

- Envelope allowlist is exactly these 12 keys
  (`ATTENDANCE_SUBMISSION_ENVELOPE_KEYS`). Any other key — including
  `version`, `checksum`, `token`, `status`, `receivedAt`, `blockers`,
  `bodyHash`, `key` — fails closed.
- There is **no sibling `version` / `checksum`** on the wire. SA computes
  `bodyHash = attendanceSubmissionBodyHash(envelope)` (FNV-1a 32 over
  sorted-keys canonical JSON, same mechanics as the Mini inbox but an
  independent function) for replay protection only. Like the Mini checksum,
  it is integrity, not an authenticity signature.
- `submissionId` is the message id for idempotency (§7). It is not employee
  or project identity.

### 1.2 Row (exact keys only)

| Key | Required | Type / rule |
|---|---|---|
| `miniLocalId` | ✔ | trimmed non-blank string; Mini-local id, opaque to SA |
| `number` | ✔ | trimmed non-blank string; display snapshot, never identity (§3) |
| `name` | ✔ | trimmed non-blank string; display snapshot, never identity (§3) |
| `normalHours` | ✔ | finite number `>= 0` |
| `overtimeHours` | ✔ | finite number `>= 0` |
| `status` | ✔ | literal `present` |
| `saEmployeeId` | — | canonical normalized SA ID, same rule as `saProjectId` (§3) |

- Row allowlist is exactly these 7 keys
  (`ATTENDANCE_SUBMISSION_ROW_KEYS`). `position`, `groupId`, `leaderId`,
  `group`, `leader`, `sueldo`/`salary`, loans/advances/photo/phone/email,
  `deletedAt`, `customSalary`, `positionSalaries`, legacy `hours`,
  `sourceEmployeeId`/`id` all fail closed.
- Hours rule: each leg finite `>= 0`, sum `> 0` and `<= 24`. `0 + 0`,
  negatives, `NaN`/`Infinity`, and sums above 24 all reject.
- One row per employee per `workDate` in v1: duplicate `miniLocalId`
  within one submission rejects; duplicate present `saEmployeeId` within
  one submission rejects. Two rows that both omit `saEmployeeId` never
  collide on the absent key.

### 1.3 `scope` is audit-only, never project authority

- `scope` carries exactly `ownerUid`, `siteId`, `sourceId` for forensics.
- Project authority comes **only** from the explicit
  `expectedSaProjectId` argument passed to `validate`/`importJSON`.
- `siteId` is **never** interpreted as `saProjectId`. A submission whose
  `siteId` differs from `saProjectId` still validates; a submission whose
  `saProjectId` differs from `expectedSaProjectId` hard-rejects before any
  store mutation, regardless of `scope`.

## 2. Versioning

1. **New schema, old schema frozen**: `mini-attendance/v1` and
   `MiniAttendanceInboxStore` are untouched. This inbox handles only
   `attendance-submission/v1` under store name `attendanceSubmissionInbox`.
2. **Exact match, fail-closed**: any other `schema`, any unknown key at
   envelope/row/`scope`/`errorSummary` level, or any missing required
   field rejects. Readers never guess.
3. **Incompatible change ⇒ new `schema`**: a new required key, a changed
   hour semantic, or a new identity rule requires a new schema literal
   with its own validator; v1 stays frozen in this doc.
4. **Compatible additions**: only new *optional* keys under the same
   schema, ignorable by old readers (which today reject unknown keys, so
   any addition ships with an allowlist update on both ends).
5. **`rosterVersion` is opaque**: compared only by equality for the
   `stale_roster` blocker (§6). Never parsed, ordered, or migrated.
6. **No auto-migration**: no path converts v1 → v2 implicitly.

## 3. Identity

- `saProjectId` and row `saEmployeeId` share one rule (local
  `normalizeAttendanceSubmissionId`, same as `normalizeSaMiniId`): string,
  trimmed, 1–128 chars, no whitespace or control chars. Anything else
  fails the whole submission closed; the inbox never skips a row.
- The **only** employee join key in v1 is
  `(envelope.saProjectId, row.saEmployeeId)` **when `saEmployeeId` exists**.
  `number`/`name` are display snapshots for review UI only.
- Consequences locked by tests: two rows may share the same `number` and
  `name` when their `miniLocalId` (and present `saEmployeeId`) differ;
  rows without `saEmployeeId` carry no join key at all
  (`'saEmployeeId' in row === false`).
- Duplicates are judged on normalized values: `'  EMP-1  '` collides with
  `'EMP-1'`; Mini-local duplicates are judged on trimmed `miniLocalId`.

## 4. Pending authority (no attendance writes)

- A valid import produces exactly **one** record with `status: 'pending'`:
  `{ key, saProjectId, submissionId, status: 'pending', receivedAt: now(), workDate, rosterVersion, blockers, bodyHash, sourceSnapshot: envelope }`.
  `receivedAt` is stamped by the inbox `now()`; client clocks are never
  trusted. `sourceSnapshot` is frozen.
- Store discipline: **one** `db.update('attendanceSubmissionInbox', …)` on
  first import; **zero** writes on duplicate (returns existing), on replay
  conflict (throws, keeps original), and on every validation/project
  rejection. The module has zero imports, touches no `attendance` store,
  no global state, no apply path, no network.
- There is **no apply/join/write route and no runtime caller** in this
  half. Turning a pending record into canonical attendance is a future,
  explicitly reviewed change — not an implicit next step.

## 5. Partial semantics (`excludedCount`, `errorSummary`)

- `excludedCount > 0` means **valid partial capture**: the device captured
  exactly `rows.length` present rows and excluded N fragments/workers that
  could not be parsed or confirmed. The record stays `pending` and valid.
- SA must **not** infer absent workers from the gap. Missing people are
  unknown, not absent. Backfill/re-capture is a future workflow decision,
  not a validator behavior.
- `errorSummary` is an audit hint only:
  `{unparsedFragments: int >= 0, codes: string[]}`. It never authorizes
  writes and never overrides `rows`.

## 6. Stale blocker (not a reject)

- `importJSON(raw, { expectedSaProjectId, expectedRosterVersion })` takes
  an optional roster reference (`currentRosterVersion` is accepted as an
  alias for mechanical symmetry with the Mini inbox).
- When a reference is supplied and `envelope.rosterVersion !== reference`,
  the record is still stored as `pending` with `blockers: ['stale_roster']`.
  Stale never rejects, never writes attendance, and never mutates the
  stored snapshot on later duplicate imports.

## 7. Idempotency scope

- Key: `(saProjectId, submissionId)` → `attendanceSubmissionKey()` =
  `encodeURIComponent(saProjectId) + '|' + encodeURIComponent(submissionId)`.
  Same key + same body ⇒ `{ outcome: 'duplicate' }`, no second write.
  Same key + different body ⇒ `AttendanceSubmissionReplayConflictError`,
  original preserved, no overwrite.
- `expectedSaProjectId` is **required and explicit** on `importJSON`.
  Project mismatch (`saProjectId !== expectedSaProjectId` after
  normalization) throws `TypeError('saProjectId mismatch')` before any
  store read/write side effect beyond the pure validation.
- `validateAttendanceSubmission(value, expectedSaProjectId?)` is pure and
  mutation-free; `importJSON` validates first, then checks replay, then
  writes at most once.

## 8. Transport neutrality

- The contract is the **bare JSON body**. Any transport that delivers the
  exact bytes (clipboard, file, QR, future Firebase) validates identically.
  Wrappers such as `{ data: … }` reject.
- `bodyHash` is order-stable: wire key order does not change the hash;
  any body byte change does.
- No Firebase, no network, no clipboard, no IndexedDB schema change ships
  in this half. The inbox takes an injected `{ db, now }` (`db.get` /
  `db.getAll` / `db.update`) so tests run on a memory double.

## 9. Boundaries: F3.10 / Firebase / future apply

- Out of scope and explicitly **not** built here: Firebase transport,
  F3.10 sync, conflict UI, apply-to-attendance, employee join execution,
  roster version resolution, and any runtime caller/wiring.
- `mini-attendance/v1`, `MiniAttendanceInboxStore`, project context, the
  attendance writer, and F3.1/F3.2 docs are frozen and untouched.
- **STOP condition** (direction-frozen): if satisfying this contract ever
  appears to require changing existing runtime/wiring, adding an apply
  path, or interpreting `scope.siteId` as `saProjectId`, stop and escalate
  instead of stretching the contract. That mapping remains documented
  pending work, not an assumption any reader may make.

## 11. Residual risks (explicit non-goals)

- `bodyHash` (FNV-1a 32) detects corruption/replay, not forgery: anyone
  can recompute it. Never treat it as a signature.
- No authentication, authorization, or device attestation in this half;
  that belongs to the transport (future F3.10/Firebase) decision.
- No cross-submission dedup beyond the composite key (e.g. two different
  `submissionId`s covering the same employee/`workDate` are two pending
  records; reconciliation is future work).
- `workDate` is format/calendar-validated only; roster-calendar,
  holiday, and range policy are future apply-side concerns.

> Regla de lectura: estos son **tres envelopes distintos**, no una sola forma con tres
> nombres. Cada tabla indica su forma exacta tal como la construyen/validam los
> productores y consumidores actuales. Nada de lo aquí escrito crea un contrato nuevo.

## 1. Los tres envelopes (formas literales)

### 1.1 `sa-roster/v1` — SA → Mini (roster canónico, productor en SA)

Productor: `buildSaMiniRosterPayload()` (`SaMiniRosterExport.js:307`).
Constantes: `SA_MINI_ROSTER_SCHEMA = 'sa-roster/v1'`, `SA_MINI_ROSTER_VERSION = 1` (`:34-35`).

```json
{
  "schema": "sa-roster/v1",
  "version": 1,
  "saProjectId": "<id SA exacto>",
  "generatedAt": "<ISO-8601>",
  "employees": [ { "saEmployeeId": "...", "number": "...", "name": "..." } ]
}
```

- Claves de envelope exactas (`SA_MINI_ROSTER_ENVELOPE_KEYS`, `:37-43`):
  `schema`, `version`, `saProjectId`, `generatedAt`, `employees`. Ni una más.
- Transporte actual: solo texto JSON al portapapeles (`shareExportMiniV1`,
  `ExportController.js:212-254`). Solo lectura: no muta storage ni registros.
- `generatedAt`: si se omite, el productor estampa `new Date().toISOString()`;
  si se provee, debe ser string no vacío (se recorta). El productor **no** exige
  forma ISO estricta al valor provisto (`SaMiniRosterExport.js:325-335`); la
  validación ISO estricta vive del lado consumidor Mini (ver §6, pendiente de
  prueba cross-repo).
- **Sin checksum**: este envelope no trae campo de integridad (ver §4).

### 1.2 `mini-attendance/v1` — Mini → SA (bandeja de asistencia)

Validador: `validateMiniAttendanceEnvelope()` (`MiniAttendanceInboxStore.js:58-98`).
Constante: `ENVELOPE_SCHEMA = 'mini-attendance/v1'` (`:2`).

```json
{
  "schema": "mini-attendance/v1",
  "eventId": "<UUID>",
  "scope": { "ownerUid": "...", "siteId": "...", "sourceId": "..." },
  "deviceId": "...",
  "clientSequence": 7,
  "rosterVersion": "roster-3",
  "capturedAt": "<ISO-8601 estricto>",
  "rows": [ { "sourceEmployeeId": "...", "number": "...", "name": "...", "status": "present", "hours": 8 } ]
}
```

- Claves de envelope exactas (`:59-62`): `schema`, `eventId`, `scope`,
  `deviceId`, `clientSequence`, `rosterVersion`, `capturedAt`, `rows`.
- `eventId` es el **id del mensaje de asistencia**: UUID (`:4-5`, `:64-65`), clave
  de dedup de la bandeja. Mismo `eventId` + mismo contenido ⇒ `duplicate`;
  mismo `eventId` + contenido distinto ⇒ `MiniAttendanceReplayConflictError`
  sin sobrescribir (`:114-128`). No es identidad de empleado ni de proyecto.
- `clientSequence`: entero seguro positivo (`:66-68`), orden del dispositivo.
- Filas: claves exactas `sourceEmployeeId`, `number`, `name`, `status`, `hours`
  (`:75`); `status` debe ser `'present'` (`:76`); `hours` finito en `(0, 24]`
  (`:77-79`).
- `capturedAt`: ISO-8601 **estricto** (`new Date(v).toISOString() === v`, `:10-14`).
- Estado de cableado (honesto): el inbox (`MiniAttendanceInboxStore`) tiene
  validador + tests pero **sin llamadores runtime** (registrado como hallazgo
  H-10 en `docs/fase-0/F0-HALLAZGOS.md:22`). El camino Mini→SA hoy cableado en
  runtime es el import WhatsApp con draft revisado (`docs/plans/mini-attendance-draft-import.md`).

### 1.3 `mini-roster/v1` — paquete roster Mini (forma de referencia en SA)

Constructor: `createMiniRosterPackage()` (`MiniAttendanceInboxStore.js:147-170`).
Constante: `ROSTER_SCHEMA = 'mini-roster/v1'` (`:3`).

```json
{
  "schema": "mini-roster/v1",
  "scope": { "ownerUid": "...", "siteId": "...", "sourceId": "..." },
  "rosterVersion": "roster-3",
  "generatedAt": "<ISO-8601 estricto>",
  "employees": [ { "id": "...", "number": "...", "name": "...", "position": "..." } ],
  "checksum": "fnv1a32:<hex>"
}
```

- Filas: `id`, `number`, `name` requeridos + `position` opcional (`:153-161`).
  **Nótese**: aquí la identidad de fila es `id` (id local Mini), no `saEmployeeId`;
  es otra forma, no la misma que §1.1.
- `generatedAt` aquí sí es ISO estricto (`iso()`, `:164`).
- `checksum` = `miniIntegrityChecksum(body)` FNV-1a 32 sobre canonización con
  claves ordenadas (`:42-49`, `:169`). Ver §4.
- Estado de cableado: sin llamadores runtime en SA fuera de sus tests
  (`MiniAttendanceInboxStoreTests.test.js:117-135`); es la forma de referencia
  contra la que Mini debe producir/consumir (ver §6).

## 2. Mapeo de nombres y semántica (no son el mismo campo con distinto nombre)

| Concepto | `sa-roster/v1` | `mini-attendance/v1` | `mini-roster/v1` |
|---|---|---|---|
| Discriminador | `schema: 'sa-roster/v1'` + `version: 1` | `schema: 'mini-attendance/v1'` (sin `version`; el `schema` ya versiona) | `schema: 'mini-roster/v1'` (sin `version`) |
| Id del mensaje/paquete | — (no hay; cada export es un snapshot) | `eventId` (UUID, dedup + replay) | — (se identifica por `rosterVersion`) |
| Secuencia de origen | — | `clientSequence` (entero ≥ 1 del dispositivo) | — |
| Marca temporal de origen | `generatedAt` (productor SA; default = ahora ISO) | `capturedAt` (captura en dispositivo; ISO estricto) | `generatedAt` (ISO estricto) |
| Marca temporal de recepción | — (clipboard: no hay recepción diferida) | `receivedAt` (**asignada por el inbox** vía `now()`, `:129`; nunca se confía en relojes del cliente) | — |
| Versión de roster | — (el snapshot es la versión) | `rosterVersion` (string opaco; solo se compara por igualdad para el blocker `stale_roster`, `:131-132`) | `rosterVersion` (string opaco, parte del cuerpo checksumeado) |
| Identidad de empleado | `saEmployeeId` dentro de `saProjectId` (ver F3.2) | `sourceEmployeeId` = **id local Mini, opaco para SA**; SA nunca lo interpreta como identidad SA | `id` = id local Mini |
| Alcance | `saProjectId` (proyecto SA canónico) | `scope: {ownerUid, siteId, sourceId}` — **no** es proyecto SA (ver §3) | `scope: {ownerUid, siteId, sourceId}` |

## 3. Dirección fuente-de-verdad y aislamiento por proyecto

- **Roster SA→Mini**: SA es fuente de verdad. El export filtra solo no-eliminados
  del proyecto activo exacto (`selectSaMiniRosterEmployees`, `:153-158`:
  `!deletedAt` + `entityInScope` + `effectiveProjectId === saProjectId`; nunca
  mezcla proyectos). Sin scope resoluble (Proyectos OFF o sin proyecto/default)
  falla cerrado con `scope-unavailable` y **no copia nada** (`:114-142`,
  `ExportController.js:159-171`).
- **Referencias puesto→proyecto**: con scope capturado, los puestos se filtran al
  proyecto activo y toda referencia cruzada aborta la exportación
  (`cross-project-position`, `:190-207`). Puesto desconocido ⇒ se omite (legacy),
  no falla (`:199`).
- **Asistencia Mini→SA**: el inbox valida `scope` triple y lo compara contra el
  `expectedScope` por clave canonizada (`:70-73`); desajuste ⇒ rechazo.
- **Prohibición explícita**: el `scope` de `mini-attendance/v1`
  (`ownerUid/siteId/sourceId`) **no** porta hoy el `saProjectId` canónico.
  `siteId ≈ sitio ⇒ mapear a `projectId` oficial** es trabajo pendiente
  documentado (`docs/fase-0/F0.2-matriz-propiedad-datos.md:44`,
  `docs/fase-0/F0.3-modelo-project-v1.md:77`). Ningún lector debe asumir
  `scope.siteId === saProjectId`.

## 4. Checksum: integridad solamente, no autenticación

- Solo `mini-roster/v1` trae `checksum` (`:169`): FNV-1a 32 no criptográfico sobre
  forma canónica. Sirve para detectar corrupción/transporte, no para probar origen.
- `mini-attendance/v1` no trae checksum en el sobre; el inbox calcula
  `bodyHash = miniIntegrityChecksum(envelope)` al importar y lo usa para
  idempotencia/detección de replay (`:117-124`).
- `sa-roster/v1` no trae checksum.
- Aviso literal congelado (`MINI_ROSTER_CHECKSUM_NOTICE`, `:176-177`):
  `Integrity checksum only; not an authenticity signature.`
  Cualquiera puede recalcular el FNV-1a; **nunca** tratarlo como firma.

## 5. Compatibilidad y política de bump de versión

1. **Coincidencia exacta, fail-closed**: el inbox rechaza `schema` distinto
   (`:63`, test `MiniAttendanceInboxStoreTests.test.js:89-102`); el productor
   SA emite literales fijados por tests (`SaMiniRosterExportTests.js:76-93`).
   Lector v1 ante sobre desconocido ⇒ rechazar, nunca adivinar.
2. **Cambio incompatible ⇒ nuevo `schema` o `version`**: p. ej. agregar una clave
   requerida, cambiar semántica de `number`, o agregar identidad nueva exige
   `sa-roster/v2` (o `version: 2`) con su propio productor/validador; v1 queda
   congelado en este documento.
3. **Adiciones opcionales compatibles**: solo claves opcionales nuevas bajo el
   mismo `schema`, ignorables por lectores viejos (que de todos modos rechazan
   claves desconocidas en el inbox estricto — ver §7: cualquier agregado debe
   acompañarse de actualización del allowlist en ambas puntas).
4. **`rosterVersion` es opaco**: string libre (`text()`, `:94`), comparado solo
   por igualdad para marcar `stale_roster` como blocker **no destructivo**
   (no toca asistencia canónica, test `:104-115`). No se parsea ni se ordena.
5. **Sin migración automática**: ningún camino convierte v1→v2 solo; la
   interoperabilidad entre versiones es decisión explícita futura (F4), no
   comportamiento implícito.

## 6. Brechas explícitas y diferidos (F3.4 / F4)

1. **F3.4 `AttendanceSubmission` no existe**: las filas `mini-attendance/v1`
   actuales (`sourceEmployeeId/number/name/status/hours`) son el borrador de
   campo, no el contrato canónico de envío (que requerirá proyecto, fecha,
   reparto por puesto, normales vs. extras). Nada de este documento debe leerse
   como cierre de F3.4.
2. **Compatibilidad cross-repo no cerrada** (solo con esta tarea): falta la
   prueba Mini que (a) consuma `docs/fase-3/fixtures/sa-roster-v1.example.json`
   con el validador Mini real, (b) fije que `siteId`⇄`saProjectId` sigue sin
   mapeo canónico, y (c) fije el mapeo `localId` Mini ⇄ `(saProjectId,
   saEmployeeId)` con invariante no-destructivo (ver F3.2 §6). Detalle exacto en
   el reporte de cierre de esta tarea.
3. **Transporte Firebase (F4)**: fuera de alcance; el clipboard es el único
   transporte implementado del lado SA y la disciplina es una escritura en éxito
   / cero escrituras en fallo (`SaMiniRosterExportControllerTests.test.js`).
4. **F3.3 Group/Leader**: fuera de este envelope (ver F3.2 §5).
5. **`generatedAt` de `sa-roster/v1`**: el productor acepta cualquier string no
   vacío provisto (`:325-335`); endurecer a ISO estricto (como `mini-roster/v1`)
   es cambio de runtime — **no** hecho aquí, propuesto para el bump que toque el
   productor.

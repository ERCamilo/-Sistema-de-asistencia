## 2. Identidad: `saEmployeeId` canónico dentro de `saProjectId`

- La identidad autoritativa es la **tupla `(saProjectId, saEmployeeId)`**
  (`SaMiniRosterExport.js:9`, `:233`). Dos proyectos pueden usar el mismo número
  de ficha sin colisionar (principio ya fijado en F1.4 con clave compuesta
  `effectiveProjectId::number`).
- `saEmployeeId` = `employee.id` exacto tras trim (`validateRowIdentity`,
  `:222-236`).
- Normalizador compartido (`normalizeSaMiniId`, `:97-104`; regla Mini):
  string con trim no vacío, máx 128 caracteres, **sin blancos internos ni
  caracteres de control**. Cualquier otra cosa ⇒ `bad-employee-id` y aborta
  **toda** la exportación (nunca se salta la fila).
- Duplicados juzgados sobre el valor normalizado (`:230-236`, `:586-598`):
  `'  dup  '` y `'dup'` colisionan ⇒ `duplicate-employee-id`, fail-closed.

## 3. `number`: operativo, nunca identidad — semántica `Number()`

- `number` se emite como el **texto recortado original** (`:251`, `:372-373`):
  `'001'` se emite `'001'`, `'  42  '` se emite `'42'`, el número JS `7` se emite `'7'`.
- Validez y colisiones se juzgan sobre la clave canónica
  `normalizeRosterNumber(value) = Number(texto recortado)` (`:77-83`), para
  paridad exacta con Mini:
  - Válidos (finitos): `'001'`, `'1.5'`, `'-3'`, `'1e2'`, `7`.
  - Inválidos (`bad-number`, fail-closed de toda la exportación): `null`,
    `undefined`, `''`, `'   '`, `'ABC'`, `'1A'`, `'Infinity'`, `'NaN'`, y todo
    tipo que no sea string/number (`:238-271`).
  - Colisionan (`duplicate-number`): `'01'` vs `'1'`, `'001'` vs `'1'`,
    `'1.0'` vs `'1'`, `'1e2'` vs `'100'`, e incluso
    `'9007199254740992'` vs `'9007199254740993'` (redondeo de grandes enteros,
    `:355-379`). Distintos (`'1'` vs `'2'`) exportan bien (`:381-393`).
- Consecuencia para Mini: **nunca unir por `number`**; es etiqueta operativa
  (coincide con el matching numérico `001 = 1` del import WhatsApp:
  `docs/plans/mini-attendance-draft-import.md`, reconciliación por número).

## 4. Opcionales: `position`, `sueldo`, `paused`

- **`position`** (display, no identidad): nombre del primer puesto
  (`positions[0]`) resuelto contra puestos **del proyecto activo**. Se omite si
  no hay puestos, si el id es desconocido (legacy: omitir, no fallar), o si el
  nombre está vacío (`:160-167`, `:375-376`; tests `:413-441`). Con scope
  capturado, referenciar un puesto de otro proyecto **falla cerrado**
  (`cross-project-position`, `:190-207`).
- **`sueldo`** (solo consentimiento explícito): únicamente cuando
  `includeSalary === true` estricto (`=== true`; `1`, `'yes'`, etc. también
  omiten — `:337-338`, tests `:177-192`). Se deriva **reutilizando** la lógica
  salarial vigente del legacy (`deriveSueldoViaLegacy` → `buildMiniExportPayload`,
  `:216-220`: prioridad `positionSalaries → customSalary → hourlyRate →
  salaryConfig` legacy, mismo redondeo a jornal diario). Sin tasa válida ⇒ se
  omite la clave (se prefiere omisión sobre `null`). Por defecto apagado; el
  opt-in se revoca al abrir/cerrar el menú de export (`ExportController.js:53-78`,
  tests de disciplina de copiado). El legacy `buildMiniExportPayload` sigue
  incluyendo sueldo por defecto (compatibilidad intacta, test `:215-218`).
- **`paused`** (presencia): solo `paused: true` cuando `active === false`.
  Activo o sin flag ⇒ **clave ausente, nunca `false`** (`:383`, tests `:443-470`).

## 6. Mapeo `localId` en Mini e invariante no-destructivo de historial

- Mini conserva sus propios ids locales (`sourceEmployeeId` en
  `mini-attendance/v1`, `id` en `mini-roster/v1`): son **opacos para SA**.
  El join SA⇄Mini es `(saProjectId, saEmployeeId)` del lado SA contra el mapeo
  local de Mini; `number`/`name` nunca son la llave del join (§3).
- Del lado SA-WhatsApp existe el mapeo deAlias
  (`MiniAttendanceAliasStore.js`): `(ownerUid, siteId, sourceId + número/nombre
  normalizados)` → `targetEmployeeId`. Sus reglas fijan el invariante:
  `forget`/`forgetAll` **tombstonean** (`active: false`, `tombstonedAt`) y
  preservan la auditoría (`:137-149`, `:182-196`); borrar coincidencias declara
  que empleados y asistencia no se borran (ver Phase 5 en
  `docs/plans/mini-attendance-draft-import.md:287-292`).
- Lado SA roster: la baja es tombstone (`deletedAt`), y el export excluye
  tombstones (`selectSaMiniRosterEmployees`, `:153-158`) en vez de
  reescribir historia (principio F0.3 §2: proyecto cerrado conserva historial;
  F1.4: tombstone `deletedAt`+`projectId` sobreviven juntos).
- Invariante para Mini (obligación a fijar en su repo, ver reporte de cierre):
  recibir un roster sin un empleado **no** borra su `localId` ni su historial;
  renombrar/recodificar (`number`/`name`) **no** bifurca la serie; la historia
  antigua sigue ligada al trabajador correcto (roadmap F3.8
  `preserve-mini-history`, pendiente).

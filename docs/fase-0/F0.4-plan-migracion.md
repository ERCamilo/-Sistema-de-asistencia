## 1. Principios de la migración

1. **Aditiva**: solo agrega información (`projectId`); nunca borra ni transforma datos existentes.
2. **Reversible**: convive con el feature flag (F0.6); flag apagado ⇒ la app ignora el concepto y todo sigue funcionando como hoy.
3. **Sin big-bang en la nube**: no hay reescritura masiva de Firestore (cuota + riesgo). La nube se va sellando sola conforme los datos circulan.
4. **Backup obligatorio ANTES** de cualquier paso que escriba datos (regla #9 del roadmap): snapshot cloud tipo `pre-migration` + recomendación de export JSON manual al usuario.
5. **Idempotente**: correrla dos veces produce el mismo resultado (los pasos detectan si ya aplicaron).

## 2. Regla semántica fundacional

> **`projectId` ausente o `null` ⇒ pertenece al Proyecto Predeterminado.**

Esta regla es la que hace posible migrar sin tocar nada al principio: la "mudanza" primero es mental (semántica), después física (sellado), y nunca urgente.

## 3. Fases internas de la migración (se ejecutarán en Fase 1, con sus propios commits)

### M1 — Semántica (cero escrituras)
- Los repositorios/servicios empiezan a resolver "proyecto efectivo" con la regla del §2.
- Se crea el Proyecto Predeterminado (`PRJ-…`, name "Mi obra", status active).
- `activeProjectId` local apunta a él.
- **Riesgo: cero** (no escribe datos). **Rollback: flag off.**

### M2 — Sellado local (IndexedDB)
- Job one-time idempotente: estampa `projectId` del predeterminado sobre registros locales de empleados, puestos, líderes, asistencia, cierres de nómina.
- Batching por chunks con yield (no bloquear UI); marca de progreso en LS (`migration.projectStamp.v1`).
- **Pre-requisito**: backup snapshot + suite de tests de F0.5 cubriendo el job.
- **Rollback**: el sello es informativo; con flag off no tiene efecto. Restore de snapshot ante cualquier anomalía.

### M3 — Sellado cloud perezoso (lazy)
- NO se reescribe Firestore masivamente. El sello sube cuando cada entidad circula naturalmente:
  - Empleados/puestos/líderes: al editarse (el watermark `entityUpload.*` existente decide cuándo subir).
  - Asistencia: al guardarse el día.
  - Settings: en su próxima escritura LWW normal.
- Lectura cloud siempre aplica la regla §2, así los documentos aún sin sello siguen siendo válidos.
- **Riesgo: bajo** (usa mecanismos existentes). **Rollback: innecesario** (aditivo).

## 4. Tratamiento por dominio

| Dominio | Tratamiento | Momento |
|---|---|---|
| Empleados/puestos/líderes | Sello M2 local + M3 cloud | Fase 1 |
| Asistencia | Sello M2/M3 por día | Fase 1 |
| Préstamos/adelantos/bonos/deducciones | **No requieren trabajo propio**: viajan dentro del empleado; el sello del empleado los cubre | — |
| Cierres de nómina | Sello M2/M3 | Fase 1 |
| Settings operativas (`payPeriod`, feriados, factores, defaults nómina) | Se copian como config inicial DEL proyecto predeterminado (D2). Las preferencias de usuario quedan globales | Fase 1 (namespacing exacto en F1.3/F1.7) |
| **Caja chica (proyectos/períodos/movimientos/tickets)** | **NO se toca.** Su `projectId` interno es otro concepto (agrupación propia). Se registra tabla de mapeo pendiente hacia el Project oficial | Post-F2 (explícitamente diferido para no huérfanar nada) |
| Aliases Mini | `siteId` queda intacto; mapeo a Project oficial se hace cuando existan >1 proyectos | Post-F2 |
| Espejo `data/current` | Gana campo con lista/versiones de proyectos cuando F1 lo defina; `exportConfig` (ajustes en curso) se limpia del espejo | Fase 1 |
| Snapshots/backups | Quedan a nivel cuenta (backup total). Backup POR proyecto es F1.9/F10.7 | Sin cambio |
| Outboxes/watermarks/locks | Infraestructura intacta; entradas nuevas llevarán `projectId` cuando el dato lo tenga | Natural |

## 5. Dispositivos múltiples

- La regla §2 garantiza que un dispositivo viejo (sin flag/código nuevo) no corrompe nada: sigue escribiendo sin `projectId` y esos registros siguen leyéndose como del predeterminado.
- Al iniciar sesión en un segundo dispositivo, M2 corre local sobre lo descargado; M3 ya no tiene nada que hacer si la nube ya circuló sellada.
- Conflictos: mismos mecanismos LWW/outbox de siempre; la migración no introduce escrituras simultáneas nuevas.

## 6. Rollback global

| Escenario | Acción |
|---|---|
| Flag apagado post-M1/M2 | App vuelve a comportamiento exacto anterior; sellos quedan inertes |
| Flag apagado post-M3 | Ídem; documentos cloud con sello extra no molestan (campo desconocido se ignora) |
| Datos inconsistentes | Restore del snapshot `pre-migration`; export JSON manual como segunda red |

## 7. Verificación del criterio "ningún dato huérfano"

1. Test automatizado (se escribirá en F0.5/Fase 1): dado un estado completo sembrado (empleados+asistencia+nómina+caja), tras M1–M2 TODO registro operativo resuelve proyecto efectivo ≠ null.
2. Contador de diagnóstico post-migración: registros locales sin sello = 0 esperado; si >0, el job se marca incompleto y reintenta (idempotencia permite re-corrida segura).
3. Cloud: no se exige sello completo (por diseño lazy); se verifica solo que ninguna lectura rompa por ausencia.

## 8. Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| Cuota Firestore por escrituras | M3 evita reescritura masiva; usa circulación natural |
| Migración interrumpida (cierre de app) | Marcas de progreso + idempotencia ⇒ re-corrida segura |
| Bug del job corrompe datos locales | Snapshot pre-migration + tests del job en F0.5 ANTES de exponerlo |
| Usuario con cuentas legadas (entidades inline en espejo) | La regla §2 las cubre sin conversión; conversión granular ya existe por schemaVersion |
| Claves LS que sobreviven al wipe (hallazgo F0.2) | No bloquean esta migración; se tratan como hardening aparte (recomendación registrada) |

## 1. Regla de clasificación propuesta

Toda entidad se clasifica en una de tres categorías:

| Categoría | Definición | Regla de migración (insumo F0.4) |
|---|---|---|
| **PROYECTO** | Dato operativo que pertenece al quehacer de una obra | Gana `projectId`; al crear proyecto nuevo nace vacío (o copiado sin movimientos) |
| **GLOBAL-cuenta** | Dato de identidad/infraestructura de la cuenta Google | No lleva `projectId`; sobrevive cambios de proyecto |
| **GLOBAL-dispositivo** | Preferencias/diagnósticos locales del dispositivo | No lleva `projectId`; nunca cruza dispositivos |

Además, sub-categoría **PLANTILLA**: configuración operativa que HOY es global pero que conceptualmente pertenece a cada obra (se copia al proyecto, no se comparte).

## 3. Hallazgo estructural principal

**Hoy `users/{uid}` ES el contenedor de todo.** No hay nivel intermedio. Introducir `projectId` significa:
- Opción A: añadir `projectId` como campo en cada entidad existente (menos invasivo, rutas Firestore iguales).
- Opción B: crear nivel jerárquico nuevo (`users/{uid}/projects/{pid}/…`) y mover subcollections (migración grande).

→ Recomendación preliminar para F0.3/F0.4: **Opción A** (campo + índices + filtros obligatorios en repositorios), porque preserva rutas, reglas actuales y el espejo; la Opción B puede ser una fase futura si V2 lo exige. Esta recomendación NO se implementa ahora; se registra para F0.3.

## 4. Riesgos de aislamiento detectados (insumo directo F1.10)

1. Claves LS que sobreviven al wipe (`attendance-entities-sync-ok`, `entityUpload.*.v1`, `attendance-error-log`, `pettyCashPersistenceMetrics:v1`, `app:debugMode`): en dispositivo compartido con cambio de cuenta pueden contaminar la nueva sesión (watermarks falsos → entidades no se suben).
2. `exportConfig` (ajustes de nómina en curso) viaja dentro del doc espejo aunque sea estado de sesión.
3. Denormalización de nombre/número en cierres: correcta históricamente, debe mantenerse bajo cualquier re-scoping.
4. Fotos: si D1 = copia de empleados entre proyectos, los blobs de Supabase podrían duplicarse salvo deduplicación por identidad.

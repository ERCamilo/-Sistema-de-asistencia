## 1. Entidad `Project` v1

| Campo | Tipo | Req. | Descripción |
|---|---|---|---|
| `id` | string | ✔ | Formato `PRJ-<timestamp base36>-<4 chars aleatorios>` — consistente con convenciones existentes (`EMP*`, `POS*`, `LEAD*`, `LOAN-*`) |
| `name` | string | ✔ | Nombre visible de la obra. Recomendación: único entre proyectos ACTIVOS (validación de UI, no constraint técnico en V1) |
| `status` | enum | ✔ | `active` \| `closed` \| `archived` |
| `schemaVersion` | number | ✔ | `1`. Toda evolución incompatible crea versión nueva |
| `createdAt` | number (epoch ms) | ✔ | |
| `updatedAt` | number (epoch ms) | ✔ | Actualizado en toda mutación |
| `closedAt` | number | — | Requerido si `status=closed/archived` |
| `archivedAt` | number | — | Requerido si `status=archived` |
| `createdBy` | string (uid) | — | Opcional en V1 (un solo usuario); se llena cuando llegue Auth multi-usuario (F4) |
| `metadata.notes` | string | — | Notas libres cortas |
| `metadata.icon` | string | — | Icono para selector/UI (opcional, default por estado) |
| `metadata.color` | string | — | Color para selector/UI (opcional) |
| `metadata.clonedFrom` | object | — | Presente solo si nació por clonación: `{ sourceProjectId, copiedAt, copiedEntities: ['employees','positions','leaders','settings'] }` — auditoría de qué se copió |

**Qué NO lleva el modelo en v1** (explícitamente fuera de alcance): organización, miembros, roles, presupuesto, dirección, coordenadas, contadores desnormalizados (los reportes calculan, nunca acumulan).

## 2. Máquina de estados

```
        crear            cerrar             archivar
  ──────────────► active ──────────► closed ──────────► archived
                     ▲                 │
                     └─── reabrir ─────┘   (archived NO reabre directo:
                          explícito         primero vuelve a closed)
```

| Transición | Regla |
|---|---|
| `active → closed` | Acción con confirmación. Bloquea: nueva asistencia, nuevos movimientos de caja, cierre/void de nómina, edición de empleados/puestos/líderes. La LECTURA y los reportes siguen funcionando siempre |
| `closed → active` | Reapertura explícita (queda registro en `updatedAt`) |
| `closed → archived` | Solo visual: deja de aparecer en listas principales. No borra nada |
| `archived → closed` | Des-archivo pasa primero por `closed`, nunca directo a `active` |

Proyecto **cerrado**: no recibe operaciones nuevas pero conserva todo su historial intacto (principio #5 del roadmap: nada se borra).

## 4. Relación con entidades existentes (opción A: campo, no jerarquía)

Toda entidad operativa gana campo opcional `projectId`:

| Entidad | Campo nuevo | Nota |
|---|---|---|
| employees / positions / leaders | `projectId` | Por decisión D1 son propiedad del proyecto |
| attendance | `projectId` | Índice compuesto eventualmente (projectId+date) |
| payrollClosures | `projectId` | |
| Movimientos/períodos de caja | ya tienen `projectId` interno → **mapear** al oficial | Migración de referencia, post-F2 |
| miniAttendanceAliases | `siteId` → mapear a `projectId` oficial | Ya trae concepto de sitio |

Regla de compatibilidad: `projectId` ausente o `null` ⇒ pertenece al **proyecto predeterminado**. Esto hace la migración aditiva y reversible (feature flag F0.6 puede ocultar el concepto sin tocar datos).

## 5. Proyecto predeterminado

- Al activar el flag de proyectos (F1.2) se crea automáticamente `Project { name: "Mi obra", status: active }`.
- Absorbe TODOS los datos existentes sin `projectId` (mecánica en F0.4).
- El usuario nunca hizo nada manual: entra y todo sigue igual, solo que ahora "vive dentro" de ese proyecto.

## 6. Siembra de configuración operativa (consecuencia D2)

Al crear proyecto (vacío o clonado) se siembran como valores iniciales DEL proyecto:
`payPeriod`, `holidays[]`, `overtimeFactor`, `holidayFactor`, `regularHoursPerDay`, `payrollDefaults`.

Origen de la siembra: defaults globales actuales (proyecto vacío) o la config del proyecto origen (clonación). Después de la siembra, cada proyecto evoluciona su config de forma independiente.

El namespacing exacto de settings-por-proyecto se define en Fase 1 (F1.3/F1.7); aquí solo queda fijado el principio de propiedad.

## 7. Semilla del contrato para Integración (insumo F3.1)

`Project Contract v1` — campos que viajarán por el envelope: `projectId`, `name`, `status`, `schemaVersion`, `updatedAt`. Los consumidores (Mini) nunca interpretan más que esto.
